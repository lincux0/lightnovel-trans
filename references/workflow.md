# 工作流：输入 → 翻译/审核 → 按需交付

> 这是可裁剪的工作流示例，不要求照搬目录。随 skill 提供的脚本仅覆盖 TXT 转换与基础检查；EPUB 提取/回写、Word、PDF、HTML 等适配需使用目标项目已有且可用的工具。先确认用户要译稿、审核、修订、EPUB 或其他交付，再选择必要步骤；默认译为简体中文，用户要求时改用繁体。

## 0. 目录结构约定

```
项目根/（示例，可按现有项目调整）
├─ books/ 或 sources/        # 原始来源（只读）；仅放入用户提供且允许用于本任务的对照译文
├─ knowledge/                # 长期资料库
│   ├─ glossary.md           # 术语表（人物/地名/组织/固定译法/符号）
│   ├─ characters.md         # 人物设定、语感、称呼总表
│   ├─ style-guide.md        # 文风指南
│   └─ dialogue/             # 可选：较长系列或角色声线差异明显时再建
├─ work/
│   ├─ extracted/vXX-jp/     # 按实际需要保存的提取结果
│   ├─ alignment/            # 可选：需要利用已授权对照译文时
│   ├─ translation-memory.jsonl   # 可选：经语义复核、允许保存的 JP→ZH 译例
│   ├─ vXX-cn/chapters/*.md  # 译文（默认与源段一一对应并保留映射）
│   ├─ vXX-progress.md       # 进度/术语备忘/日志
│   ├─ vXX-cn-vertical.epub  # 可选：用户要求 EPUB 时的回写备份
│   └─ scripts/              # 项目实际使用的工具（不假设本 skill 随附 EPUB/Word 转换器）
└─ output/                   # 仅在用户要求文件交付时使用
```

## 1. 输入适配与提取（目标：可追溯的工作文本）

按输入格式产出可追溯的工作文本；无需强行让所有输入变成完全相同的结构。随附 `txt_to_md.py` 仅输出 `chapters/` 与 `toc.md`；`chapters.json`、`full.md`、`images/` 仅在所选打包流程确实需要时再建。记录来源文件及章节/段落位置，便于回查：

- `chapters/*.md`：可采用 `# 标题` 首行、一行一源段；保留有意义的行首空格与独立分隔符。输入若为软换行，先结合版面重建段落，不把排版换行当作段落边界。
- `chapters.json`：如后续工具需要，记录 id / role / title / sources / 字数。
- `toc.md`：章节索引；`full.md`、`images/` 按实际需要生成。

### 1.1 EPUB（有原版）

- 从 `META-INF/container.xml` 定位实际 OPF，按 manifest/spine 确认阅读顺序，结合 NCX/nav 辅助切章，不假定包内目录与文件名。
- 章节切分：按 spine 顺序归入 section，角色命名稳定（frontmatter / toc / prologue / ch01..chNN / interlude / epilogue / afterword / bonus1.. / illustration / colophon），保证多卷间可直接配对。
- ruby/tcy：保留底字与读音等辅助信息供译者判断；外字图片可能是正文字符，须保留引用或先确认字符内容，不得因提取方便直接丢弃语义。
- 插图以标记保留位置；核对脚注、链接及其他行内内容是否被完整提取。
- 提取校验：核对来源映射、段落、图片引用及关键行内内容；计数差异用于定位问题，数量相等也不能证明没有漏译或丢失语义。

### 1.2 TXT（常见于网络流传版）

- 编码：优先确认来源声明或用户指定；`auto` 仅按 UTF-8 → CP932 → EUC-JP 回退尝试，解码成功也可能识别错误，必须抽样核对文字。
- 章节切分：用正则匹配章节行（第N章 / 第N話 / プロローグ / エピローグ / 幕間 / あとがき / 特別短編 等）；模式参数化，不同作品先抽样确认。
- 段落：默认一行一段；软换行版先人工确认段落重建方式。脚本的 `blank` 模式保留首行缩进及独立分隔符，也可重复指定 `--separator`。
- 插图：TXT 无内嵌图；如另有图片目录，按文件名顺序在对应位置插入 `![illust]` 标记（位置需人工确认）。
- 参考脚本：`scripts/txt_to_md.py`（编码回退与章节切分；仅产出 `chapters/` 与 `toc.md`）。它拒绝非空输出目录；`--min-chapter-lines` 只给出警告，不删除章节。先抽样确认规则再运行。

### 1.3 Word / docx

- 段落与标题：可解析 `word/document.xml` 的 `w:p`；标题样式作为章节切分点，无样式时按章节规则辅助判断。DOCX 可包含 ruby；也可能遗漏或乱序读取表格、文本框、脚注/尾注、图片及关系，提取后必须抽查。
- 图片：docx 本质是 zip，图片在 `word/media/`；按 `document.xml.rels` 的 r:embed 关系把图插入到段落位置（插画页可近似）。
- 注音（ruby）：可能真实存在于 DOCX XML 中。若工具能读取，应保留底字和读音供翻译判断；若已丢失，不要猜测恢复，读音可在有依据时另行核对。
- 工具：可使用目标项目已有的 `python-docx`；无第三方依赖时用标准库 `zipfile` + `xml.etree.ElementTree` 读取 XML。`lxml` 是第三方库。
- 如后续流程需要，可整理成带章节标题、分段文本和插图标记的工作文本；不要求与 EPUB 提取目录完全同构。

### 1.4 其他来源

- HTML / 网页：去标签转 md（保留段落与标题层级），图片下载到 images/。
- azw3 / mobi：先用 calibre（ebook-convert）转 EPUB，再走 1.1。
- PDF：仅当无其他来源时考虑；优先文本层提取，扫描版需 OCR，质量风险高，段落结构需人工校对。

> 提取完成后抽查章节、段落、注音、图片及脚注等关键内容。仅统计数量不能证明语义完整；格式适配工具缺失时，先确认可用工具和遗漏风险。

## 2. 资料库（两种条件分支）

### 有可用的对照译文（可选）

- 对用户提供或项目已有、可用于本任务的中文译文按需对齐；TM 随当前项目维护，不自动上传或向其他项目复制语料。
- 对齐分数只用于筛选候选，必须回看日文和中文确认语义后才能入库；任何固定分数不能代替人工判断。
- **glossary.md**：人物、地名、组织、固定译法、高频词、标点/符号处理；只收录经核对与复现的译法；官方译法明显冲突时以原文为准且不写入。
- **characters.md**：自称、称呼、语感、例句 + 称呼总表（说话人 × 对象，核对用）。
- **style-guide.md**：文风通则、称呼本地化、标点规则。
- **对白分桶（可选）**：仅在篇幅、系列长度或声线差异值得维护时建立；归属不确定的句子不作角色规则。以上资料均按规模按需建立。

### 无官方中译（只有日文原版）

- **术语先行**：开译前识别重要专名与称呼；规模较小时可边译边记录，不要求为单卷先建空库。
- **自建 TM（可选）**：将项目已有且经过日文语义复核的自译作为候选译例；跨作品参考不覆盖本作品约定，不在任务范围外自动收集或保存语料。
- **风格基线**：写一份 style-guide（文风、称呼、标点）；可参照同类出版译作定调，但仅作风格参考，不建 TM 条目。
- **对白分桶（可选）**：可从已复核译文归集；不确定说话人时标为未知，不据此推断角色规则。
- 详细做法与检查清单见 [no-official-cn.md](no-official-cn.md)。

**维护原则**：新卷只添加经确认的信息；核对上下文后再沿用旧条目。同一词因人物关系、时间或语境而采用不同译法时可以成立，应记录适用条件，不强行统一。

## 3. 翻译（逐场景）

- 场景划分：以作者的分隔符、章节边界、时间/地点/视角转换为界；长度按上下文与处理能力决定，不固定段数或一次翻整卷。
- 每个场景动笔前：如有可用 TM，按人物/术语/表达查找已复核译例；是否适用仍以当前日文语境为准。
- 默认一源段对应一译段，保留映射以便校验；句内分句可按中文表达调整。若用户授权拆分或合并段落，记录每个译段对应的源段范围。随附 `verify_alignment.py` 只支持默认的一对一行结构，不能用于证明拆并后的映射正确。
- 行文：中文自然、符合轻小说阅读习惯；对白按角色语感（characters.md + dialogue/）；吐槽、敬语、口癖分别处理。
- 记录：每章完成更新 `work/vXX-progress.md`（状态表 + 术语备忘 + 日志）；新称呼/术语记入待并入清单，卷末并入 knowledge。

## 4. 自检与 QA

- 默认逐章检查源段映射、标题、分隔符与插图位置；拆并段时检查显式源范围映射。行数与标记检查只证明结构对应，不证明语义完整。
- 全卷 QA：核对已确认的专名/禁用表记、未经处理的假名、术语一致性、可疑长度差、重复及格式残留。按作品把假名允许保留项列清楚。
- 长度比、字数、段落数等仅筛出待复核项；它们不能证明漏译或语义正确，也不要求把启发式告警清零。人工确认实质问题并记录例外后再进入用户要求的后续交付。

## 5. 打包（两种路径）

**路径 A：用户要求 EPUB 且有原版 EPUB（可选）**

- 以日文原版 EPUB 为底本回写前，确认项目工具能保留结构与必要注音/外字语义；不得默认移除可能承载读音或正文字符的内容。
- 目录页 / NCX / nav 标签中文化；奥付与版权声明不回写（保留日文）。
- 按用户需要生成成品；竖排中间版或备份仅在原版排版与检查流程适用时保留。

**路径 B：用户要求 EPUB 但无原版可回写（可选）**

- 按 EPUB 3 要求自建容器、包元数据、导航、内容和资源；NCX 按兼容需求选择，目录名不限定。
- 正文直接生成用户需要的排版；例如横排成品为 `output/vXX-cn.epub`，不必先造竖排中间版。
- 结构、样式与验证要点见 [epub-packaging.md](epub-packaging.md)。

若用户只需要译稿、审核结果或其他格式，跳过 EPUB 打包。只有用户要求制作 EPUB 时才选择相应构建路径与排版方向。

## 6. 横排转换（仅适用时）

- 需要从竖排转横排时，适配实际 CSS 与模板、翻页方向及必要元数据，原文保留页保留正确语言；布局提示随成品更新。
- `vrtl→hltr` 与固定 OPF 替换仅适用于相应模板。详细条件和样式示例见 [epub-packaging.md](epub-packaging.md)。

## 7. 按交付目标验证

- **回写验证**（仅路径 A）：按实际预期核对文件差异、结构、链接/锚点、目录和关键译文；确认正文中未经处理的假名，并核对已记录的保留项。
- **方向转换验证**（仅进行了排版方向转换时）：检查转换差异、方向/语言元数据、分隔符和关键内容。
- **渲染抽查**：仅在本次交付包含 EPUB 且环境具备相应工具时进行；检查实际指定的排版方向、缩进、分隔符与标题。
- **自建 EPUB（路径 B）验证**：无原版可 diff，改为——①EPUB 结构合法（mimetype/OPF/nav/链接/锚点）；②正文与译稿段落映射一致；③样式生效（渲染抽查）；④确认未经处理的假名及明确保留项；⑤如有旧版成品，再与旧版逐文件 diff。
- 交付物仅包含用户要求的格式；不默认生成 EPUB、竖排备份或额外文件。

## 8. 修订/审核回合

- 纯审核或只读请求：逐项回原文核对并报告结论，不修改译稿、不打包。
- 用户明确要求修订后，才修改确认成立的问题；复核未授权的疑点时先说明依据，不擅自改写。
- 只有本次目标包含 EPUB 时才重新打包，并对交付文件做对应验证；不默认执行发布。
